# Project Guidelines

Flutter/Dart app to track media seen. See `README.md` for the product overview,
`DOCS/export-format.md` for the import/export format and `DOCS/i18n.md` for localization.

## Code Style

- Files/dirs `snake_case`; classes `PascalCase`; members `camelCase`; private with `_`.
- Use `debugPrint`, never `print`.
- Naming suffixes: `Provider`, `Repository` / `RepositoryImpl`, `DataSource`.
- Lint is enforced by `analysis_options.yaml` (stock `package:flutter_lints/flutter.yaml`,
  no custom rules). Don't add linter config here; rely on `flutter analyze`.

## Architecture

Feature-first, layered under `lib/features/<feature>/{data,domain,presentation}`.
Shared entities live in `lib/core/domain/entities/`.

The layers are **asymmetric** — do not assume every feature has all three:

| Feature | Layers present |
| --- | --- |
| `achievements`, `search` | full `data` + `domain` + `presentation` |
| `media_details` | `data` + `presentation` (no `domain`; entities in `lib/core`) |
| `discovery`, `home`, `library`, `profile`, `settings`, `together` | `presentation` only |

Key wiring:

- **DI** — get_it + injectable (`@LazySingleton(as: X)`, `@module`, `@InjectableInit`).
  Entry point `lib/core/di/injection.dart`; DB in `lib/core/database/app_database.dart`;
  initialized in `main.dart` via `await init(locator)`.
- **State** — provider `ChangeNotifier`, wired in `MultiProvider` in `main.dart`
  (`SearchProvider`, `SettingsProvider`, `AchievementProvider`, and the session states
  `SwipeSessionProvider` / `TogetherSessionProvider`, which must outlive a change of tab).
- **Tabs** — `AppTab` (`lib/core/navigation/app_tab.dart`); never a tab index. The selected
  tab lives in `SearchProvider.selectedTab`; the shell is `MainPage` + `AppTabBar`.
- **Errors** — `AppException` hierarchy in `lib/core/error/exceptions.dart`.

`search` owns `MediaRepository`. For deeper context see `DOCS/ai-guidelines.md`.

## Build and Test

Run from the repo root:

```bash
flutter doctor                                            # check environment
flutter pub get                                           # install deps
dart run build_runner build                               # REQUIRED after fresh clone
flutter analyze                                           # lint
flutter test                                              # tests
```

`build_runner` regenerates gitignored Isar `*.g.dart` and injectable
`injection.config.dart`. Always run it after a fresh clone or when models/DI change.

## Conventions

- **Commits and PR titles** — Conventional Commits: `<type>(<scope>)!: <desc>`, for every
  commit message **and** every PR title. Types `feat`/`fix`/`docs`/`style`/`refactor`/`perf`/
  `test`/`build`/`ci`/`chore`/`revert`/`bump`; scope optional and free (feature name, e.g.
  `export`, `media_details`, `back`). Details in `.ai/rules/commits.md`.
- **Language & Clean Code** — Strictly English for all code (class names, methods, variables,
  comments, test descriptions) and commit messages/PR titles. Zero code duplication: never
  introduce duplicate French aliases, dual-language boilerplate, or redundant definitions. All
  user-facing UI text is localized via `.arb` files (`app_en.arb` template and `app_fr.arb`),
  never hardcoded strings in code.
- **Branches** — readable, referencing the issue: `<type>/<issue>-<slug>`, e.g.
  `feat/233-readable-export-filename`.
- **Tests** — mirror source path + `_test.dart`; `group('...', () { test('should ...', ...) })`.
  Mock with `mocktail`; shared mocks in `test/helpers/mocks.dart`; load fixtures with
  `fixture(name)` from `test/helpers/fixture_reader.dart`. Real Isar tests use `test/tmp_*`
  scratch dirs; widget tests guard with `Platform.environment.containsKey('FLUTTER_TEST')`.

## Gotchas

- **Generated files** — `*.g.dart` and `*.config.dart` are gitignored; regenerate with
  build_runner, never hand-edit.
- **Isar** — persistence comes from the community fork `isar_community` (v3 API), **not**
  the upstream `isar` package, which is abandoned and ships 4 KB-aligned Android
  binaries. Do not switch back; imports are `package:isar_community/isar.dart`.
- **Achievements** — source of truth is `assets/achievements/definitions.json` (stable ids).
  `ACHIEVEMENTS.md` is a non-authoritative summary; don't treat it as the schema.
- **Config** — `.env` is bundled as an asset but never referenced in code; the TMDB key is
  stored in SharedPreferences under `tmdbApiKey`.
- **i18n** — UI strings live in `lib/l10n/app_<code>.arb` (`app_en.arb` is the template);
  use `context.l10n.<key>` from `lib/core/l10n/l10n.dart`, never hardcoded text in new UI.
  `lib/l10n/generated/` is regenerated by `flutter pub get` / `flutter gen-l10n`; don't
  hand-edit it. Adding a language = new ARB file + one `supportedAppLanguages` entry +
  achievement `translations` (see `DOCS/i18n.md`). Match TMDB genres by id
  (`GenreUtils.getGenreIdByName`), never by English name. TMDB requests get `language` automatically from `LocaleService`;
  the search filter for content language is `originalLanguage` (`with_original_language`).
- **Scratch** — `test/tmp_*` dirs and `test/tmp_io_test.dart` are disposable; ignore them.

## Workflow

Write Conventional Commit messages and PR titles per the rules above. Install the local
hook once: `pip install pre-commit && pre-commit install --hook-type commit-msg`.
Verify with `flutter analyze` and `flutter test` before considering a change done.
CI (`.github/workflows/ci.yml`, Flutter pinned there) runs on every PR: `build_runner`, `flutter analyze --no-fatal-infos`, `dart format --set-exit-if-changed lib test` (non-blocking for now), `flutter test --coverage`. `pr-title.yml` checks the PR title and every commit subject
against Conventional Commits. `release.yml` runs on every push to `main`: `ci.yml` analyze/test, then release-please (release PR `chore(release): vX.Y.Z`; merging it tags and builds the APK + AAB, checked for 16 KB page alignment by `tool/check_16kb_alignment.sh`). Never bump `version:` or push tags by hand; see `DOCS/releasing.md`.

### Stacked PRs & Restacking After Squash Merge

PRs are merged into `main` via **Squash and Merge** (required by `release-please` so each PR title becomes a single commit on `main`).
When a parent branch `A` is squash-merged, its squashed commit arrives on `main` with a brand new SHA. Stacked child branches (`main` ← `A` ← `B` ← `C`) still contain the original un-squashed commits of `A`. A standard merge or naive rebase replays those commits and triggers false conflicts.

**Procedure to update stacked branches after parent merge:**

1. **One-time Git setup:**
   ```bash
   git config --global rebase.updateRefs true
   ```
   Keep "Automatically delete head branches" enabled on GitHub so merged parent branches trigger automatic retargeting of child PRs to `main`.

2. **Rebase child branch using `--onto`:**
   ```bash
   git fetch origin
   git rebase --onto origin/main <old-parent-tip-or-branch> <child-branch>
   ```
   - For a single child `feat/302-xxx` previously based on `feat/301-xxx`:
     ```bash
     git checkout feat/302-xxx
     git rebase --onto origin/main <old-tip-of-301> feat/302-xxx
     ```
   - For a multi-level stack (`main` ← `A` ← `B` ← `C`), checkout the **top** of the stack (`C`) with `rebase.updateRefs true`:
     ```bash
     git switch feat/303-xxx
     git rebase --onto origin/main <old-tip-of-301>
     ```
     `--update-refs` automatically moves intermediate branch refs (`B`) along with `C`.
   - If the local parent branch ref was already deleted, find `<old-parent-tip>` via `git merge-base` or the last commit SHA of the parent branch from its PR.

3. **Verify clean commit log:**
   ```bash
   git log --oneline --graph origin/main..<child-branch>
   ```
   Must display **only** the commits specific to the child branch(es), without replaying squashed parent commits.

4. **Force push with lease:**
   ```bash
   git push --force-with-lease origin <child-branch>
   # If stacked branches were updated via updateRefs:
   git push --force-with-lease origin feat/302-xxx feat/303-xxx
   ```

5. **Merge order:**
   Always merge in topological order (parent first, child next), one PR at a time. Keep dependency stacks shallow (2-3 levels max). Once a foundation PR is merged, branch new work directly off `main`.
